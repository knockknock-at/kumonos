# KUMONOS 要件

## 1. 目的

KUMONOSは、指定されたフォルダおよびAIエージェントの会話ログを継続的に読み取り、個人の試行錯誤を再利用可能な組織知へ変換する。

単なる全文検索や会話要約ではなく、ログに含まれる問題、解決方法、失敗、手順、設計判断、ツールを知識Nodeとして抽出し、それらの関係、出典、成熟度を管理する。

## 2. 対象利用者

| 利用者 | 主な利用目的 |
|---|---|
| AI活用担当者 | 個人のAI利用から有用なノウハウを残す |
| チーム管理者 | 複数人に共通する知見や重複作業を発見する |
| 標準化担当者 | 正式な手順・ツールへ昇格する候補を確認する |
| システム管理者 | 対象範囲、モデル接続先、権限、実行周期を管理する |
| ナレッジ閲覧者 | Markdown、Obsidian、HTMLなどで知識を探索する |

## 3. 基本原則

1. **疎結合**：特定のAI、共有ストレージ、ノートアプリを必須にしない。
2. **入力不変**：対象ログや成果物を変更しない。
3. **出典優先**：すべての知識を元ログ、セッション、成果物へ追跡可能にする。
4. **差分処理**：変更された入力だけを再処理する。
5. **再構築可能**：生成した知識とグラフを入力から再生成できるようにする。
6. **人間による昇格**：組織標準や正式環境への反映を自動確定しない。
7. **非信頼入力**：ログや文書内の命令を実行せず、分析対象データとして扱う。
8. **日本語優先**：日本語の業務会話、英語の技術用語、略語が混在する前提で設計する。

## 4. 機能要件

### FR-01 入力範囲の設定

- 複数の対象フォルダまたはGitHubリポジトリを設定できる。
- include／exclude globを設定できる。
- ファイル形式、最大サイズ、更新期間を制限できる。
- 対象ごとに所有者、部署、プロジェクト、機密区分などの既定値を設定できる。

### FR-02 Connector

MVPでは以下のConnectorを対象とする。

- Codex session／rollout JSONL
- Claude Code project／conversation JSONL
- 汎用JSONL
- Markdown
- プレーンテキスト
- GitHub repository（GitHub.com、GitHub Enterprise Cloud、GitHub Enterprise Server）

将来、PDF、Word、チャットエクスポートなどを追加可能なインターフェースにする。

GitHub ConnectorのMVPでは、README、`docs/`、Markdown、テキスト、選択した設定ファイルとソースコードを読み取る。Issue、Pull Request、Discussionは権限と量が異なるため、別機能として後から追加する。

### FR-03 差分検出

- パス、サイズ、更新日時、内容ハッシュを記録する。
- 新規・更新・削除・移動を識別する。
- 同一内容の重複コピーを再処理しない。
- 処理途中で停止した場合に安全に再開できる。
- GitHubではrepository ID、解決済みcommit SHA、file blob SHAを記録し、名称変更とbranch更新を区別する。

### FR-04 正規化とノイズ除去

- 会話ログを共通のSession／Turn形式へ変換する。
- token accounting、進捗通知、重複plan、内部telemetryなどを除外する。
- user、assistant、tool result、session metadataを区別する。
- `cwd`、セッションID、時刻、使用ツールを保持する。

### FR-05 秘匿処理

- API key、token、password、認証情報らしい文字列を検出し、LLM送信前にマスクできる。
- 除外対象ファイル・フォルダをLLMへ送信しない。
- 元ログと生成物で異なる保持ポリシーを設定できるようにする。
- 秘匿処理の件数と理由を監査ログへ記録する。

### FR-06 知識抽出

少なくとも以下のNode種別を抽出する。

- `problem`
- `solution`
- `failure`
- `playbook`
- `decision`
- `tool`
- `project`
- `concept`
- `candidate-standard`

会話の時系列要約ではなく、再利用可能なテーマ単位へ編成する。

### FR-07 関係抽出

少なくとも以下のEdge種別を扱う。

- `solves`
- `caused-by`
- `uses`
- `validated-by`
- `contradicts`
- `supersedes`
- `observed-in`
- `related-to`
- `candidate-for-standardization`

### FR-08 統合・重複排除

- 類似する知識を既存Nodeへ統合できる。
- 日本語名、英語名、略語、表記揺れをaliasとして扱える。
- 矛盾する内容を上書きせず、出典と時点を分けて保持する。
- 統合判断のconfidenceと理由を保存する。
- 自動統合の閾値未満はレビュー候補へ送る。

### FR-09 出典・検証状態

すべてのNodeおよび重要なEdgeに以下を保持する。

- 元ファイルの識別子またはパス
- セッションID
- 発生日時
- 所有者または入力スコープ
- プロジェクト
- 抽出元範囲のハッシュ
- `extracted`／`inferred`／`ambiguous`
- confidence
- 検証に使用したコード、テスト、README、成果物

### FR-10 知識の成熟度

- `draft`、`observed`、`repeated`、`candidate-standard`、`approved`、`operationalized`を管理する。
- 異なるユーザー・プロジェクト・日時での出現回数を集計する。
- 成熟度を自動提案できるが、`approved`以降は人間だけが確定できる。

### FR-11 出力

以下の出力を提供する。

- Node／Edge／provenanceを表現するversion付きの機械可読データ
- Obsidian互換Markdown
- 通常のMarkdownリンクを使うポータブルMarkdown
- JSONグラフ
- GraphMLグラフ
- ブラウザだけで開ける静的HTML
- 標準化、矛盾、統合、要検証、横展開の判断候補データ
- 処理結果・エラー・秘匿処理の監査ログ

静的HTMLでは、グラフと判断候補の一覧を同じデータから表示する。グラフだけを判断根拠にせず、候補ごとに理由、根拠、推奨する次の行動を示す。

### FR-12 レビュー

- 新規Node、統合候補、矛盾、標準化候補をレビュー待ちとして一覧化する。
- accept、reject、defer、merge先変更を記録できる。
- レビュー前後の内容と判断者を追跡できる。
- 入力元へ自動的に書き戻さない。
- MVPの静的HTMLは閲覧専用とし、判断結果は管理者画面からSQLiteへ記録する。
- CLIからも同じレビュー処理を呼び出せるが、一般の管理操作には必須としない。

### FR-13 実行方法

- CLIでscan、compile、export、status、rebuildを実行できる。
- Windowsタスクスケジューラなどから非対話実行できる。
- dry-runを提供する。
- 一つの出力領域に対して同時書き込みを防止する。

### FR-14 モデル接続

- LLM providerを交換可能にする。
- 通常のAPIへ直接接続する方式と、組織指定のAI Gatewayを経由する方式を選択できる。
- Direct APIでは、APIキー、モデル名、任意のBase URLを設定できる。
- Gateway方式では、管理画面で生成された設定内容を貼り付けて取り込める。
- Gatewayの貼り付け内容をプログラムとして実行せず、許可した接続項目だけを解析する。
- 接続方式やAPI形式が異なっても、同一versionの入力・出力schemaと検証処理を使用する。
- Gateway障害時にDirect APIへ自動的に切り替えず、意図しない送信先変更を防止する。
- 利用可能モデル、送信可能な入力区分、最大token、予算上限を設定できる。
- provider障害時に、入力状態を失わず再試行できる。
- LLMを使わないscan／status／export操作を可能にする。

### FR-15 アプリ起動・管理者画面

- Windows用インストーラーまたはセットアップ手順から導入できる。
- デスクトップまたはスタートメニューから管理者画面を起動できる。
- 初回設定ウィザードで、参照先、出力先、LLM接続、利用者表示、実行周期を設定できる。
- 管理者画面から、確認実行、更新して公開、前回結果を開く、状態確認を実行できる。
- 参照先、出力先、利用者台帳、用語集、レビュー待ち、スケジュールを画面から管理できる。
- 確認実行では、LLMへ送信せず、対象件数、除外件数、送信予定量、権限、推定費用を確認できる。
- 閲覧者はKUMONOSやObsidianを導入せず、ブラウザだけで公開済み結果を確認できる。

### FR-16 利用者と用語の標準化

- 利用者を変更しない`owner_id`へ対応付け、実名の`display_name`と匿名用の`privacy_label`を分けて保持する。
- OSログイン名、メールアドレス、フォルダ名を、そのまま永続的な利用者IDにしない。
- 対応付けできない入力を自動確定せず、管理者画面の未割当一覧へ送る。
- 正式用語、別名、旧名称、誤用候補をversion付き用語集で管理する。
- 元ログの表現は出典として保持し、LLMだけで誤りを訂正・上書きしない。
- 誤用の疑いはレビュー候補とし、人間が承認した用語だけを正式表示へ反映する。
- 利用者の役職や熟練度ではなく、独立した出典、テスト、成果物、矛盾の有無で知識の確度を評価する。

### FR-17 保存・公開・差分更新

- 設定、Graph Store、manifest、レビュー履歴、cache、log、backupはKUMONOS実行端末へ保存する。
- SQLiteをネットワークドライブ上で直接更新しない。
- ネットワーク上の出力先には、閲覧・交換用の再生成可能な成果物だけを公開する。
- 出力を`.staging/<run-id>`へ生成・検証し、成功時だけ`current`へ切り替える。
- 公開に失敗した場合は、前回成功した`current`を維持する。
- 一つのprofileを一つの`security_scope`へ対応させ、異なる閲覧範囲の入力とGraph Storeを分離する。
- 入力と出力が相互の配下に入る設定を拒否する。
- 入力追加・変更時は、その入力と関係するNode、Edge、観測数、成熟度、判断候補だけを再計算する。
- 入力削除時は出典を`inactive`とし、承認済み知識を自動削除せず、根拠消失としてレビューへ送る。
- schema、normalizer、prompt、用語集のversionを保存し、必要な範囲だけを再処理できる。

## 5. 非機能要件

### NFR-01 セキュリティ

- 実行アカウントが読める範囲だけを対象とする。
- 生成物によって元データより広い閲覧権限を与えない。
- community pluginや外部実行コードを必須にしない。
- 入力に含まれるプロンプトインジェクションを命令として解釈しない。
- LLMのAPIキー、Gateway認証情報、貼り付けた設定原文を、設定ファイル、ログ、生成ノートへ保存しない。
- LLM接続先のhostを許可リストで制限でき、TLS検証を無効化しない。
- GitHub認証情報を設定ファイル、ログ、生成ノートへ保存しない。
- 異なる閲覧権限のGitHubリポジトリを、同じ出力領域へ無条件に統合しない。
- APIキーと認証情報は実行端末のOS資格情報ストアへ保存する。
- 一つのprofileに異なる機密区分を混在させない。
- 静的HTMLへ認証情報やLLM呼び出し機能を含めない。

### NFR-02 信頼性

- 同じ入力と設定から、構造的に同等の結果を再生成できる。
- manifest更新と生成物更新を途中状態のまま確定しない。
- 失敗したファイルがあっても、他の独立ファイルを処理できる。
- Graph Storeの更新をtransactionで確定し、公開物はstagingで検証してから切り替える。

### NFR-03 可観測性

- 処理件数、skip件数、エラー件数、LLM利用量、生成・更新Node数を記録する。
- 秘密値を含めず、使用した接続profile、API形式、モデル、request IDを記録する。
- 一つの知識が、いつ・どの処理で・何から作られたか追跡できる。
- run IDと、schema、normalizer、prompt、用語集の各versionを記録する。

### NFR-04 性能・コスト

- 差分処理を標準とする。
- LLMへ送る前に決定的な前処理でノイズを削減する。
- 実行ごと・日ごとのtokenまたは費用上限を設定できる。
- 初期MVPの具体的な性能目標は、サンプルログ計測後に決定する。

### NFR-05 ポータビリティ

- Windowsを最初の主要対象とする。
- ネットワークドライブまたは同期フォルダを入力・出力に利用できる。
- Obsidianをインストールせずに全処理を実行できる。
- 保存形式を特定ベンダーだけが読める形式に限定しない。
- 閲覧者の端末では、ブラウザ以外の専用ソフトを必須にしない。

## 6. MVP受入条件

1. 2〜3人分のCodex／Claude Codeログを設定で指定できる。
2. 少なくとも一つの公開GitHubリポジトリを設定し、READMEとMarkdownを読み取れる。
3. GitHub Enterprise Serverの`api_base_url`を設定でき、GitHub.comを前提にしたURLを内部へ固定しない。
4. 2回目以降は新規・更新された入力だけを処理する。
5. 「問題と解決」「失敗と注意点」「再利用可能な手順」を抽出できる。
6. 各生成知識から元セッションまたはGitHubのcommit・pathを追跡できる。
7. 同じ知見が複数入力にある場合、重複ページを増やさず統合候補を作れる。
8. MarkdownとJSONグラフを生成できる。
9. `index.html`をブラウザで開き、標準化候補、矛盾、要検証項目を確認できる。
10. GraphMLを生成し、外部のグラフ分析ツールへ受け渡せる。
11. Obsidianなしで処理を完了でき、生成MarkdownをObsidianで開ける。
12. 入力ログとGitHubリポジトリを変更しない。
13. 秘密情報らしい文字列をLLM送信前にマスクできる。
14. 各判断候補から、対象知識と元入力まで追跡できる。
15. Direct APIと組織指定のAI Gatewayで、同じfixtureから同じversionのKnowledge Candidateを生成できる。
16. Gateway設定の貼り付け時に、貼り付け内容をプログラムとして実行しない。
17. 接続設定、実行ログ、生成物にAPIキーやGateway認証情報を残さない。
18. Windowsで管理者画面を起動し、参照先、出力先、LLM接続、利用者台帳を設定できる。
19. 利用者を安定した`owner_id`へ対応付け、profileごとに実名または匿名表示を選べる。
20. 正式用語と誤用候補を分け、元ログを変更せずに管理者がレビューできる。
21. Graph Storeはローカルに保持し、成功した場合だけネットワーク上の`current`を更新できる。
22. 入力追加時に差分だけをLLM処理し、関係する既存知識と判断候補を更新できる。
23. 管理者画面からレビューを承認、保留、却下できる。

## 7. MVP対象外

- リアルタイム共同編集
- 全社横断の細粒度ACL管理
- 完全自動の組織標準化・正式環境反映
- 全Office形式の高精度解析
- Obsidian community pluginの開発
- 独自のチャットUI
- 静的HTMLからLLMへ追加質問する機能
- 大規模グラフDBの導入

## 8. 未決事項

- MVPの実装言語と、インストーラーの具体的な配布・更新方式
- モデルの初期値と、接続先ごとの利用可能モデルの確認方法
- embeddingをMVPへ含めるか
- 入力規模、実行周期、保持期間の初期目標
- Node／Edge schemaのversioning方式
