# KUMONOS アプリMVPの起動・設定・運用設計

## 1. 目的

技術者がCLIで試すだけでなく、組織の管理者が初期設定し、一般の閲覧者がブラウザで結果を確認できるアプリMVPにする。

MVPでは、設定と実行を行う「管理者」と、生成結果を見る「閲覧者」を分ける。

## 2. 起動方法

### 初回

1. 管理者がWindows用インストーラーまたは`SETUP.bat`を実行する。
2. デスクトップとスタートメニューへ「KUMONOS」を登録する。
3. 初回起動時に設定ウィザードを開く。
4. 設定完了後、業務文書をLLMへ送らない確認実行を行う。
5. 管理者が内容を確認してから最初のcompileを実行する。

### 2回目以降

管理者は管理者画面から次を選ぶ。

- `更新して公開`：差分を処理し、成功後に閲覧用出力を更新する。
- `結果を開く`：前回成功した`index.html`を開く。
- `確認実行`：ファイルやLLM送信量を確認するが、知識を確定しない。
- `状態を確認`：最終成功日時、処理件数、エラー、費用を表示する。

通常運用では、同じ処理をWindowsタスクスケジューラから非対話実行できるようにする。

## 3. 管理者画面

MVPの管理者画面には次の機能だけを置く。

| 画面 | 操作 |
|---|---|
| ホーム | 更新して公開、結果を開く、確認実行、最終実行結果を見る |
| 参照先 | フォルダやGitHubを追加・停止し、include／excludeを設定する |
| 出力先 | ネットワーク上の公開先を選び、書込み権限を確認する |
| LLM接続 | Direct APIまたは組織指定Gatewayを設定し、接続テストする |
| 利用者 | `owner_id`と表示名を対応付け、実名・匿名表示を選ぶ |
| 用語集 | 正式用語、別名、誤用候補を確認する |
| レビュー | 統合、矛盾、標準化候補を承認・保留・却下する |
| スケジュール | 自動実行の時刻と有効・無効を設定する |

静的な`index.html`は閲覧専用とし、変更操作と認証情報を管理者画面へ集約する。

## 4. 参照先の指定

管理者は「参照先を追加」から次を選ぶ。

### フォルダ

- ローカルフォルダまたはUNC形式のネットワークパスを選択する。
- Connectorを自動判定し、必要なら手動で変更する。
- include／exclude、最大ファイルサイズ、更新期間を指定する。
- 所有者、部署、プロジェクト、機密区分を設定する。

### GitHub

- repository URLを入力する。
- GitHub.comまたはEnterpriseのAPI URLを接続profileへ保存する。
- README、`docs/`などの初期対象を表示し、管理者が変更できるようにする。
- private repositoryではOS資格情報ストアの参照名だけを設定へ保存する。

### 登録時の検査

- 読み取り可能か。
- 出力先の配下を参照していないか。
- `.env`、秘密鍵、認証情報、実行ファイルなどが除外されているか。
- 異なる機密区分を一つのprofileへ混在させていないか。

MVPでは、一つのprofileを一つの`security_scope`へ対応させる。公開、社内、限定案件を処理する場合はprofileとGraph Storeを分ける。

## 5. 出力先と保存場所

### ローカル端末

```text
%ProgramData%\KUMONOS\profiles\<profile-id>\
├── config\
│   └── kumonos.yaml             # 秘密値を含まない設定
├── state\
│   └── kumonos.db               # 知識・出典・レビュー履歴の正本
├── cache\                       # 再取得可能な一時データ
├── logs\                        # 秘密値を除いた実行ログ
└── backups\                     # Graph Storeの世代バックアップ
```

SQLiteをネットワークドライブ上で直接更新しない。ネットワーク切断やファイルlockingの差を避けるため、Graph StoreはKUMONOS実行端末へ置く。

APIキーとGateway認証情報は設定ファイルへ書かず、Windows資格情報マネージャーへ保存する。

### ネットワーク上の公開先

```text
<output-root>\
├── current\
│   ├── index.html
│   ├── notes\
│   │   └── KNO-0001.md
│   ├── graph.json
│   ├── graph.graphml
│   ├── decisions.json
│   └── reports\
│       └── latest-run.json
├── history\
│   └── <run-id>\
└── .staging\                    # 生成途中。閲覧対象外
```

生成中は`.staging/<run-id>`へ書き、全fileの検証に成功した後だけ`current`を切り替える。失敗時は前回成功した`current`を残す。

出力先の選択時に、書込み権限、空き容量、入力との包含関係、閲覧ACLを確認する。

## 6. 利用者の識別と表示

OSのログイン名、メールアドレス、フォルダ名をそのまま知識の識別子にしない。管理者が次の利用者台帳を管理する。

```yaml
owners:
  - owner_id: USR-0007
    display_name: 山田 太郎
    privacy_label: 営業部・利用者07
    organization_unit: 営業部
    aliases:
      - yamada
      - user-folder-07
    active: true
```

- `owner_id`は変更しない内部IDとする。
- `display_name`は実名表示を許可したprofileだけへ出す。
- 匿名表示では`privacy_label`を使う。
- 対応付けできない入力は勝手に新しい人物として確定せず、管理者画面の「未割当」へ送る。
- 氏名が変わっても過去の出典は同じ`owner_id`へ結び付ける。

閲覧用画面の初期表示は「3名の利用者で確認」のような集計とし、profileの規則で許可された場合だけ個別名を表示する。

## 7. 用語と品質の標準化

文章の長さや専門的な表現ではなく、同じKnowledge Candidate schemaへ変換して形式を揃える。

利用者の役職や熟練度をconfidenceへ直接加点しない。テスト、成果物、複数の独立した入力、利用条件、矛盾の有無を根拠にする。

用語は次の構造で管理する。

```text
Term
├── term_id
├── canonical_label
├── aliases
├── deprecated_labels
├── suspected_misuse
├── status
├── approved_by
└── approved_at
```

処理規則は次の通りとする。

1. 元ログの表現は変更せず、出典として保持する。
2. 承認済み用語集に一致した場合は`canonical_label`で表示する。
3. 略語、英語名、旧名称はaliasとして保持する。
4. 明らかに見える誤りでもLLMだけで確定せず、「用語確認候補」へ送る。
5. 管理者が承認した内容だけを用語集の正式項目へ反映する。
6. 過去のNodeは、用語集versionが変わったときに影響範囲だけ再表示・再評価する。

誤った内容そのものは用語修正で上書きせず、`contradicts`または`verify`候補として扱う。

## 8. 視覚化とレビュー

閲覧者はネットワーク上の`current/index.html`をブラウザで開く。必要な操作は、絞り込み、Node選択、根拠リンクの確認だけとする。

Obsidianは`notes/`を見る任意の選択肢であり、視覚化の生成には不要とする。

承認、保留、却下、統合先変更は管理者画面から行い、結果をローカルのGraph Storeへ記録する。次の公開時に`decisions.json`と`index.html`へ反映する。

静的HTMLからLLMへ追加質問する機能はMVP対象外とする。APIキーや認証情報をHTMLへ含めず、独自のチャット画面も作らない。

## 9. 入力追加時の更新

入力追加時は全ログをLLMへ送り直さず、差分更新する。

1. 新規・変更・削除をmanifestで検出する。
2. 新規・変更部分だけを正規化、秘匿処理、知識抽出する。
3. 新しい候補を既存Nodeの検索indexと比較する。
4. 候補と関係する既存Node、Edge、観測数、成熟度、判断候補を再計算する。
5. SQLite transactionで一括確定する。
6. 出力一式を`.staging`へ再生成し、成功後に公開する。

入力が削除された場合、出典を`inactive`にして観測数と判断候補を再計算する。人間が承認した知識は、根拠が消えても自動削除せず「根拠消失」としてレビューへ送る。

全再構築は次の場合だけ行う。

- 管理者が明示的に`rebuild`を実行した。
- Node／Edge schemaの互換性がない変更を行った。
- 正規化、Sanitizer、抽出promptのversion変更で全件再評価が必要になった。
- Graph Storeの修復が必要になった。

各Nodeへ最後に処理した`schema_version`、`normalizer_version`、`prompt_version`、`glossary_version`を保存し、古いものだけを再処理できるようにする。

## 10. MVP受入条件

1. Windowsでインストールし、デスクトップから管理者画面を起動できる。
2. 画面からフォルダ、GitHub、出力先、LLM接続を設定できる。
3. 入力と出力の包含、読み書き権限、機密区分を事前検査できる。
4. 利用者を安定した`owner_id`へ対応付け、実名または匿名表示を選べる。
5. 誤用候補を元ログの改変なしにレビューできる。
6. 「更新して公開」が成功したときだけ`current`を切り替える。
7. 入力追加時に差分だけをLLM処理し、関連する既存知識を更新できる。
8. 閲覧者はKUMONOSやObsidianなしで`index.html`を確認できる。
9. 管理者画面から判断候補を承認、保留、却下できる。
10. 静的HTMLに認証情報やLLMへの追加質問機能を含めない。
