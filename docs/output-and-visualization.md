# KUMONOS 出力データと視覚化の設計

## 1. この設計で実現すること

KUMONOSの出力は、知識を保存するだけでなく、次の判断につなげる。

1. 組織の標準手順として検討する
2. 似た知識を一つにまとめる
3. 矛盾する方法のどちらを採用するか調べる
4. 根拠が弱い知識を実際に検証する
5. 別のプロジェクトへ横展開する
6. 今は何もしないと決める

KUMONOSは判断候補と根拠を提示する。標準化、削除、Operationへの移動は、人が決定する。

MVPの`index.html`は安全に配布できる閲覧専用画面とする。判断結果はCLIで記録する。

```text
kumonos review DEC-0001 --accept --comment "共通前処理として試行する"
kumonos review DEC-0002 --defer  --comment "性能計測後に再確認する"
```

## 2. MVPの出力フォルダ

```text
output/
├── index.html                 # 最初に開く判断画面
├── notes/                     # 人が読む知識ノート
│   └── KNO-0001.md
├── graph.json                 # システム連携用の知識グラフ
├── graph.graphml              # Gephiなどへの受け渡し
├── decisions.json             # 判断候補
└── reports/
    └── latest-run.json        # 今回の処理結果

state/
└── kumonos.db                 # 差分・出典・レビュー履歴の正本
```

`output/`はすべて再生成可能とする。`state/kumonos.db`は内部状態であり、閲覧者へそのまま配布しない。

## 3. 出力と判断の対応

| 人が知りたいこと | 表示する信号 | 次の行動 |
|---|---|---|
| 標準化する価値があるか | 複数の人・案件での出現、検証済み根拠、未解決の矛盾 | 標準化レビューを開始する |
| 同じ話が重複していないか | 類似度、共通する別名、同じ問題との接続 | 統合する、別知識のまま残す |
| 方法が食い違っていないか | `contradicts`関係、観測日時、環境、検証結果 | 条件を比較して採用方法を決める |
| AIの提案だけで終わっていないか | テスト、成果物、実行結果の有無 | 検証タスクを作る、保留する |
| 横展開できるか | 複数プロジェクトでの再現、必要条件、失敗例 | 別案件で試す、共通手順化する |

## 4. `index.html`の構成

画面はネットワーク図だけにしない。判断候補の一覧を主役とし、グラフは前後関係を理解するために使う。

```text
┌─────────────────────────────────────────────────────────────┐
│ 要確認 4件  標準化候補 1件  矛盾 1件  根拠不足 1件         │
├──────────────┬──────────────────────────┬───────────────────┤
│ 絞り込み     │ 知識ネットワーク         │ 選択した知識      │
│ 種類         │                          │ 要約               │
│ 成熟度       │    ○────○                │ 成熟度・観測数     │
│ プロジェクト │     ╲  ╱                 │ 根拠へのリンク     │
│ 要確認だけ   │      ○                   │ 推奨する次の行動   │
├──────────────┴──────────────────────────┴───────────────────┤
│ 判断候補                                                   │
│ [高] 標準化候補 … 理由 … 根拠 … 推奨する次の行動          │
│ [高] 矛盾       … 比較する二つの方法 …                     │
└─────────────────────────────────────────────────────────────┘
```

### ネットワーク図の表示規則

- Nodeの色は成熟度を表す。
- Nodeの形または短いラベルは知識の種類を表す。
- Nodeの大きさは観測数を表すが、極端に大きくしない。
- 線は関係の種類を表し、初期表示では重要な関係だけを表示する。
- Nodeを選ぶと、要約、根拠、関連プロジェクト、推奨行動を右側へ表示する。
- 初期表示は「要確認の知識とその近傍」に絞り、全件表示による毛玉状態を避ける。

色だけに意味を依存せず、文字ラベルも併記する。

## 5. `graph.json`

グラフを別の画面やシステムから利用するための交換形式である。

```json
{
  "schema_version": "1.0",
  "generated_at": "2026-08-16T10:00:00+09:00",
  "nodes": [
    {
      "id": "KNO-0001",
      "type": "playbook",
      "title": "変更検出に内容ハッシュを使う",
      "summary": "更新日時だけに依存せず、内容ハッシュで差分を確認する。",
      "lifecycle": "repeated",
      "confidence": 0.93,
      "evidence_count": 4,
      "independent_scope_count": 3,
      "projects": ["Project A", "Project B"],
      "last_observed_at": "2026-08-15T18:20:00+09:00",
      "note_path": "notes/KNO-0001.md"
    }
  ],
  "edges": [
    {
      "id": "EDG-0001",
      "source": "KNO-0001",
      "target": "KNO-0002",
      "type": "contradicts",
      "confidence": 0.88,
      "evidence_count": 2
    }
  ]
}
```

### 必ず保持する情報

- 安定したID
- 知識の種類と成熟度
- 人が読める要約
- 観測数と独立した入力範囲の数
- 検証状態
- 関連プロジェクト
- 最終観測日時
- Markdownノートへの相対パス
- Node同士の関係と、その根拠数

詳細な出典はMarkdownノートとGraph Storeへ保持する。閲覧用JSONには、出力先の権限を越える情報を含めない。

## 6. `decisions.json`

判断候補をグラフから独立して扱うためのデータである。画面の一覧、CLIレビュー、将来の通知機能が同じデータを利用する。

```json
{
  "schema_version": "1.0",
  "items": [
    {
      "id": "DEC-0001",
      "kind": "standardize",
      "priority": "high",
      "status": "open",
      "target_node_ids": ["KNO-0001"],
      "title": "差分検出手順を共通化する",
      "reason": "3つの独立した入力範囲で確認され、テスト結果もあるため。",
      "signals": {
        "independent_scopes": 3,
        "projects": 2,
        "evidence": 4,
        "validated_evidence": 2,
        "unresolved_conflicts": 0
      },
      "recommended_action": "標準手順の担当者を決め、Operationへの反映可否をレビューする。",
      "caution": "ネットワークドライブでの処理時間を追加確認する。"
    }
  ]
}
```

### 判断候補の種類

| 値 | 意味 |
|---|---|
| `standardize` | 組織標準として検討する |
| `resolve-conflict` | 矛盾を比較して解消する |
| `merge` | 重複の可能性を確認する |
| `verify` | 根拠を追加する |
| `reuse` | 別案件への横展開を検討する |

優先度だけを表示せず、候補になった理由と元の数値を必ず併記する。候補生成の閾値は設定可能とする。

## 7. Markdownノート

ノートは、Obsidianを使わなくても読める通常のMarkdownとする。

```markdown
---
id: KNO-0001
type: playbook
lifecycle: repeated
confidence: 0.93
---

# 変更検出に内容ハッシュを使う

## 要点

更新日時だけに依存せず、内容ハッシュで差分を確認する。

## 適用条件

- ネットワークドライブや同期フォルダを入力にする場合

## 根拠

- Project A / session-001 / テスト成功
- Project B / session-014 / 再実行で重複なし

## 関連

- [更新日時だけで変更を判定する](KNO-0002.md)
```

元ログへのリンクまたは識別子は残すが、閲覧者が権限を持たない入力を出力側から見えるようにしてはならない。

## 8. 判断候補を作る方法

MVPでは、説明可能な規則を使って候補を作る。例として次の初期値を置き、実データで調整する。

### 標準化候補

- 独立した入力範囲が2以上
- 検証済み根拠が1以上
- confidenceが0.80以上
- 未解決の重大な矛盾がない

### 矛盾解消候補

- `contradicts`関係がある
- 両方に利用実績または検証結果がある

### 要検証候補

- 複数回参照されている、または再利用価値が高い
- ただし、実行結果、テスト、成果物による裏付けがない

これらは自動決定の条件ではなく、人に見せる条件である。

## 9. 実装方針

- PythonのNetworkXでグラフ構造と集計を扱う。
- MVPの`index.html`では、PyVis相当の操作可能なグラフを判断画面へ埋め込む。
- 外部通信なしでネットワークドライブ上から開けるよう、必要なデータをHTMLへ埋め込む。
- `graph.json`をシステム連携、`graph.graphml`をGephiなどの詳細分析に使う。
- Obsidianは`notes/`を閲覧する任意のツールとする。
- HTML、Markdown、JSON、GraphMLはGraph Storeから再生成する。
- MVPのGraph StoreはSQLiteとし、判断結果も同じSQLiteへ記録する。

## 10. MVPで判断できることの受入確認

サンプルまたは実データを使い、閲覧者が次の問いへ答えられることを確認する。

1. 今、標準化を検討すべき知識は何か。
2. なぜ候補になったのか。
3. どの人・案件・会話に根拠があるか。
4. 競合する方法や注意点はあるか。
5. 次に誰が何を確認すべきか。

グラフが表示できても、この5問に答えられなければMVP完了とはしない。
